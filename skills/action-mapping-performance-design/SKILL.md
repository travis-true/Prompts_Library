# Action Mapping & Performance Design

Turn a request for *information delivery* into a defensible decision about *workplace performance*. Use three modes: **Discover** (problem and causes), **Design** (action map and practice), **Review** (existing solution). This is an independent implementation aid informed by performance consulting, backward design, and Cathy Moore's publicly described action-mapping principles. It is **not** an official Cathy Moore product and does not reproduce the book.

## When to use / boundaries

**Trigger examples:** "We need training on X," "Is training the answer?", "Build an action map," "Find performance barriers," "Make this course activity-first," "Design realistic practice," "Review this participant workbook," "Connect our training to business outcomes."

**Do not automatically use** for simple copyediting, styling a PowerPoint, creating a graphic, or writing finished production assets when the performance goal/design is already approved and the request is strictly about presentation. Use only within the user's authorized scope; do not replace an existing project coordinator, production agent, or approval authority.

**Core principles**
1. Trace work backward: **outcome → observable job actions → barriers → interventions → practice/support → evidence**.
2. Differentiate evidence, reports, assumptions, proposals, and unresolved unknowns. A request for training is not proof that training is needed.
3. Non-training options are first-class: clearer processes, permissions, better tools, manager expectations, job aids, workflow redesign, and feedback.
4. If practice is useful, prioritize realistic actions and decisions with consequences and feedback; provide only the information learners need to perform the action.
5. Evaluate transfer and business performance where feasible; **completion, satisfaction, knowledge, confidence, independent task performance, and workplace outcomes are distinct measures**.
6. Work with human stakeholders/SMEs when evidence is required. Never invent validation, interviews, baselines, approvals, metrics, technical access, or tool tests.

## Start: identify scope and safeguards

1. Determine the requested mode. If unspecified, choose **Discover** for an initial training request; **Design** when outcomes/actions are established; **Review** when existing learning assets are supplied. Say which mode was selected.
2. Identify available source evidence, audience, current job situation, intended output, existing project IDs/revisions, approved decisions, and holds. Do not search unrelated projects or prior client material without authorization. If the user supplied a portable project record, treat it as the control document.
3. Verify current authorization and boundaries. **An approval for analysis is not approval for detailed design, production, deployment, or changes to another agent's project record.** Never claim a document has been externally saved or that another specialist has been invoked.
4. If a consequential detail blocks a valid result, ask **one focused question at a time**; otherwise produce a clearly labeled provisional draft using `Unknown / Not provided / To validate`. Do not force a numeric goal or interview that has not occurred.
5. Use safe fictional or synthetic practice data where regulated, confidential, personal, or company data would be inappropriate. Never reveal sensitive information or change permissions.

## Mode 1 — DISCOVER: performance diagnosis

Use [performance discovery gate](assets/performance-discovery-gate.md) and [barrier diagnostic](assets/barrier-diagnostic.md).

**D1. Performance problem.** Separate the sponsor's *request* from the *performance gap*. Record observed difficulty, who is affected, task context, frequency/impact, and evidence/source. Capture a measurable outcome if one exists; otherwise propose a measurable *candidate* without pretending the baseline or target is known.

**D2. Actions.** List specific on-the-job verbs plus objects, conditions, and evidence: "Find a decision from a specified meeting and confirm the source" rather than "Understand OneNote." Separate critical actions from prerequisite facts. Prioritize provisionally by impact, frequency, risk, and difficulty; don't invent priority weights.

**D3. Barriers.** For each priority action, investigate: environment/access/tools, process/work design, role expectations/incentives, knowledge, practiced skill/decision making, and other/unknown. Ask what capable people do, whether employees can perform under realistic conditions, and whether an accessible job aid or workflow fix would resolve the gap. Classify each cause as **Observed / Reported / Hypothesis / Unknown**.

**D4. Intervention decision.** For each barrier, distinguish **train/practice**, **performance support**, **process/tool/access change**, **manager/stakeholder action**, and **investigate first**. A blended recommendation is legitimate. Do not claim training alone can fix an environment barrier.

**D5. Output.** Return a filled discovery gate, critical-action/barrier table, candidate interventions (including non-training choices), missing evidence, and the decision/approval needed before Design. **Stop** if Discover-only scope was authorized.

## Mode 2 — DESIGN: action map and activity architecture

Use [action map template](assets/action-map-template.md), [activity brief](assets/practice-activity-brief.md), and [scenario guidance](references/scenario-guidance.md).

**G1. Preserve source decisions.** Use approved outcomes and action/object goals as constraints. If a proposed change conflicts with an approved plan, put it under **Change proposed — approval required**, not inside the approved baseline. If essential evidence is missing, mark the design **provisional**, never approved.

**G2. Map the chain.** For each priority workplace action give stable IDs (`A-01`, etc.), supporting evidence, barrier/constraint, intervention, practice (if needed), just-in-time information, performance evidence, and transfer signal. Use `N/A — no practice justified` rather than forcing instruction for an access or process problem.

**G3. Activities first.** Draft at **high level** unless detailed design is specifically authorized: realistic situation and materials; decision/action; plausible alternatives/errors; consequence-based feedback; available job aid; accessibility and technology dependencies; observable success evidence. Design independent task performance separately from supported rehearsal when needed.

**G4. Prototype & validation plan.** Recommend one representative low-fidelity activity for testing before full production. Specify who needs to test it and what is *not yet observed*. Do not carry out tests, create finished teaching assets, or schedule sessions without authorization.

**G5. Measurement chain.** Propose **practice evidence → independent task evidence → workplace transfer signal → business metric**. State data source, owner, timing, feasibility, risks, and unknown baseline. Never conflate a learner's confidence with ability or one anecdote with a group-level baseline.

**G6. Output.** Deliver an action map with trace IDs, high-level practice architecture, non-training interventions, support resources, proposed measurement, unresolved dependencies/holds, and approval request. Stop at the user's authorized stage.

## Mode 3 — REVIEW: performance-alignment audit

Use [review checklist](assets/review-checklist.md) and [quality rubric](references/quality-rubric.md).

**R1. Read only supplied or authorized materials.** Identify title, type, version, intended audience, current authorization, and whether actual performance data exists. Note absent evidence as `Cannot determine` instead of a failure.

**R2. Audit traceability.** Test: measurable performance goal; critical actions; root-cause diagnosis and non-training options; realism of practice; feedback/consequences; on-demand aids; independent evidence; transfer measurement; content load; accessibility/operational constraints. Use **Supported / Partial / Missing / Cannot determine / Not applicable**, with source locations and a short rationale. No fabricated scores.

**R3. Recommend changes by severity.** Report 3–5 highest-leverage proposed improvements, expected benefit, existing source/approval constraints, and what must be validated first. Distinguish **editorial improvement**, **design proposal**, and **scope change**. Do not silently revise approved wording, learning outcomes, activity sequence, assessments, or slide references.

**R4. Output.** Produce an audit summary, evidence-based finding table, changes requiring approval, and a concise next-step handoff. If content editing is separately authorized, preserve approved content unless exact changes are authorized.

## Reusable handoffs and quality controls

- Produce the [handoff packet](assets/handoff-packet.md) when work feeds another agent or phase. Include project ID; source versions; artifact ID/version/status; evidence ledger; decisions; unresolved items; approvals/holds; permitted next steps; and explicit **not authorized** actions.
- Use version labels such as `AM-001 v0.1 — PROPOSED`. **Never manufacture approval IDs.** Human approval must be recorded from supplied evidence before labeling something approved.
- In a live pilot, do not assume technical procedures, platform entitlements, observation timing, or assessor reliability have been validated. Treat reported participant observations differently from direct system observation and reviewer decisions.
- In training-related sensitive domains, default to safe dummy data; do not expose private information, bypass access limits, or suggest changing entitlements without authorization.
- State when evidence is thin; distinguish one observed attempt from a trend; offer an evidence-gathering plan instead of manufacturing percentages.
- **Before submitting:** apply the [quality rubric](references/quality-rubric.md): traceability, causal humility, training/non-training decisions, authenticity, minimal information, measurement separation, accessibility, approvals, and scope compliance.
