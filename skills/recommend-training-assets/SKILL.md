# Training Asset Recommendation and Routing

Recommend an evidence-based asset package before production. Diagnose the performance need, route it to the appropriate asset types, explain the reasoning, expose gaps, and obtain approval before building.

## Governing rules

- Recommend the smallest effective package. Do not default to every possible asset.
- Diagnose the needed behavior or decision before choosing a format.
- Separate training needs from process, access, incentive, policy, staffing, communication, or system problems.
- Use only supplied or authoritative source information for factual content.
- Label facts, assumptions, inferences, recommendations, and unresolved gaps distinctly.
- Never invent process steps, policy, system behavior, ownership, approval, validation evidence, or publishing status.
- Treat brand, accessibility, information classification, platform, deadline, and file-format requirements as routing constraints.
- Prefer point-of-need support when a person must recall detailed steps during work.
- Include practice and feedback when successful performance requires judgment or skill.
- Include evaluation only when it will answer a defined decision question.
- Stop after recommendation and routing unless the user explicitly authorizes planning or production.

## Workflow

### 1. Establish the requested mode

Determine whether the user wants:

1. recommendation only;
2. recommendation plus production plan; or
3. recommendation followed by asset production.

If unclear, default to recommendation only.

### 2. Review available evidence

Inspect the request, attachments, existing assets, authoritative sources, and user answers. Identify:

- desired workplace behavior or decision;
- audience, experience, role, location, language, and accessibility needs;
- trigger and moment of need;
- frequency, complexity, consequence, variability, and expected lifespan;
- delivery environment and available technology;
- current assets and known performance evidence;
- source authority, information classification, and approval requirements;
- schedule, budget, staffing, format, branding, publishing, and maintenance constraints.

Ask grouped clarifying questions only when missing information could materially change the route. Prefer three to five high-value questions in one round. Continue until the route is sufficiently reliable; target roughly 95% confidence when the user permits questions.

If the user requests an immediate recommendation, proceed with explicit assumptions and confidence limits.

### 3. Diagnose the performance need

Classify the primary cause:

- knowledge or skill;
- information retrieval or memory;
- judgment or decision support;
- communication or awareness;
- motivation, incentives, or consequences;
- workflow, policy, role, or ownership;
- tool, access, usability, or technical failure;
- capacity, staffing, or environmental constraint;
- mixed or unresolved.

Do not prescribe training as the primary response when the dominant cause is not learnable. Recommend the appropriate non-training intervention and add training or performance support only where it contributes.

### 4. Select the intervention pattern

Choose one primary pattern:

- live learning;
- self-paced learning;
- point-of-need performance support;
- practice or simulation;
- communication and reinforcement;
- blended program;
- non-training intervention with supporting enablement.

Read [references/routing-matrix.md](references/routing-matrix.md) when the route is complex, high-risk, mixed, or contested.

### 5. Select and size the asset package

Read [references/asset-catalog.md](references/asset-catalog.md) to select:

- one primary asset or experience;
- only the supporting assets required for delivery or use;
- reinforcement assets when behavior must persist after launch;
- measurement assets tied to an actual decision;
- operational assets needed for ownership, publishing, accessibility, support, or maintenance.

Reuse or revise suitable existing assets before recommending new ones. Distinguish:

- required for minimum viable effectiveness;
- recommended because it materially improves transfer, access, or risk control;
- optional enhancement;
- not recommended.

### 6. Test the route

Confirm that the recommendation:

- addresses the diagnosed cause;
- fits the moment of need and delivery environment;
- is usable by the full audience;
- can be built from available authoritative sources;
- avoids unnecessary duplication;
- has realistic ownership and maintenance;
- includes appropriate practice for skill or judgment;
- includes point-of-need support for detailed or infrequent work;
- respects risk, privacy, accessibility, and approval requirements;
- does not claim unsupported effectiveness or validation.

For high-risk work, require authoritative content, accountable human approval, version control, test evidence, and a review cadence before release.

### 7. Produce the recommendation brief

Use the compact structure in [references/output-template.md](references/output-template.md). Lead with the recommended package, then explain the diagnosis and tradeoffs.

Always include:

- recommendation summary;
- diagnosed need and evidence;
- package table with priority and purpose;
- assets to reuse, revise, create, or retire;
- delivery and reinforcement approach;
- measurement approach, or why none is needed;
- assumptions, gaps, risks, and required decisions;
- confidence level;
- approval gate and next step.

Provide no more than two viable alternatives unless the user asks for more. Explain what would make each alternative preferable.

## Routing shortcuts

- **Simple, stable, low-risk task:** concise job aid or QRG; add a demonstration only if the interface is difficult.
- **Infrequent, detailed task:** point-of-need guide, checklist, or decision support; avoid recall-heavy training.
- **New skill requiring practice:** instruction, demonstration, guided practice, independent practice, feedback, and a take-away reference.
- **High-judgment work:** scenarios, decision support, facilitated debrief, and performance-based assessment.
- **Broad awareness change:** concise campaign, manager reinforcement, FAQ, and support path; do not use a full course unless behavior must change.
- **Software rollout:** role-based learning plus searchable task support and troubleshooting; avoid feature tours disconnected from work.
- **Existing deck without transfer support:** preserve the deck when suitable and add only the missing practice, facilitator, participant, reinforcement, or reference assets.
- **Unsupported or conflicting source material:** pause content production; recommend source reconciliation and approval.

## Quality controls

Before delivering the recommendation:

- verify that every required asset has a distinct job;
- remove assets justified only by convention;
- confirm that the primary asset matches the dominant moment of need;
- confirm that evaluation measures the intended behavior or decision;
- mark unavailable evidence as `NOT PROVIDED` or `NOT VERIFIED`;
- state who must approve unresolved high-risk decisions;
- keep recommendations platform-neutral unless the user supplied a platform constraint.
